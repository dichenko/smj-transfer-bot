# ТЗ: веб-панель управления мостом Telegram ↔ MAX

Дата: 28 сентября 2026 года. Версия: 1.0. Этот документ дополняет [основное ТЗ](TECHNICAL_SPEC_RU.md). Панель предназначена для владельца и доверенных администраторов; публичной регистрации нет.

## 1. Назначение и границы

Через веб-панель администратор добавляет и управляет парами **чат ↔ чат** и **канал → канал**, видит, в какие Telegram-чаты/каналы и MAX-чаты/каналы добавлены боты, проверяет их права и отслеживает доставку сообщений. Для добавления пары не нужны SSH, редактирование файла конфигурации или перезапуск контейнера. Из `.env` читаются только секреты, адрес панели и список разрешённых Telegram ID администраторов; сами пары хранятся в БД.

Панель работает в составе того же проекта и использует существующего Telegram-бота для входа. Второго Telegram-бота и второго процесса, получающего обновления по тому же токену, не создавать. Существующая первая пара чатов сохраняет своё поведение и показывается в панели как «Функционал №1» в режиме просмотра; изменение её маршрута и прав через обычный интерфейс запрещено.

## 2. Экраны панели

| Экран | Что видно | Действия администратора |
| --- | --- | --- |
| Обзор | Число активных пар каждого типа, новые обнаруженные объекты, ошибки за сутки, размер и возраст очереди, последняя успешная доставка | Перейти к проблемной паре или журналу |
| Пары чатов | Telegram-чат ↔ MAX-чат, направление MAX → TG, статус, политика отправителей, последние доставки | Добавить, проверить права, изменить параметры новой пары, приостановить/возобновить, архивировать |
| Пары каналов | Telegram-канал → MAX-канал, статус, последние посты | Добавить, проверить права, приостановить/возобновить, архивировать |
| Куда добавлены боты | Два списка: Telegram и MAX; тип, название, точный ID, права, активность, привязка к паре | Фильтр «без пары», поиск, копирование ID, открыть историю событий, начать создание пары |
| Журнал добавлений | Когда и куда добавили/удалили бота, изменили его права или название объекта; источник Telegram/MAX | Фильтр по дате, платформе, типу и объекту |
| Доставки | Время, пара, направление, тип медиа, исходный/целевой ID, статус, попытки, краткая ошибка | Фильтр, открыть детали, повторить только безопасно повторяемое задание |
| Аудит панели | Кто, когда и какую пару создал, изменил, включил, остановил или отправил тест | Просмотр и фильтр; записи не редактируются через панель |

На каждом экране видны текущее время последнего обновления данных и явное состояние «бот не подключён / права потеряны / данных ещё нет». В журнале добавлений показывать **события присутствия бота**, а в журнале доставок — **судьбу конкретного сообщения**; не смешивать эти два журнала. Тексты сообщений, содержимое медиа и токены в интерфейсе не показывать по умолчанию.

Ориентир главного экрана:

```text
Обзор | Пары чатов | Пары каналов | Куда добавлены боты | Доставки | Аудит

Активные пары: 3 чата / 18 каналов     Новые объекты без пары: 2
Очередь: 4 задания                     Ошибки за 24 часа: 1

Требует внимания
  MAX · канал «Новости» · бот добавлен сегодня · ID … · создать пару
  Пара «Фото» · потеряно право публикации · открыть настройки

Последние доставки
  12:30 · Новости TG → MAX · видео · отправлено
  12:28 · Рабочий чат MAX → TG · фото · ошибка · открыть детали
```

## 3. Вход через команду `/admin`

Единственный способ получить новую сессию панели — написать `/admin` **в личный чат Telegram-боту**. Настройка `ADMIN_TELEGRAM_USER_IDS` в `.env` содержит точные числовые Telegram user ID через запятую; пустой список закрывает вход всем. `ADMIN_WEB_URL` задаёт публичный HTTPS-адрес панели. Telegram-имя, username, номер телефона, членство в чате и права администратора канала для веб-входа не используются. Отправка `/admin` в группе/канале не должна создавать ссылку или раскрывать список админов. Поступившее личное сообщение проверять по `ctx.from.id`, а не по `chat.id`, тексту сообщения или `username`.

Последовательность:

1. Бот получает `/admin` в личном чате и проверяет Telegram user ID по allowlist из `.env`.
2. Разрешённому пользователю бот отправляет личное сообщение со ссылкой вида `https://admin.example.ru/login#<случайный-токен>`, срок действия **5 минут**. Ссылка одноразовая; новый запрос `/admin` отменяет предыдущие неиспользованные ссылки этого администратора.
3. Страница открывается по HTTPS без авторизованных данных. Токен после `#` не отправляется браузером в URL запроса и не попадает в обычные access logs. Страница показывает кнопку «Продолжить вход»; только после её нажатия передаёт токен в `POST /api/auth/start`, очищает адресную строку и показывает «Подтвердите вход в Telegram». Обычный просмотр ссылки сканером не запускает вход.
4. Сервер создаёт ожидающий запрос входа, привязанный к открывшему страницу браузеру отдельным случайным `HttpOnly` cookie, и присылает **тому же разрешённому Telegram user ID** сообщение с кнопками «Подтвердить вход» / «Отменить». В сообщении указать время и примерную платформу браузера. При нажатии бот заново проверяет ID нажавшего и текущий allowlist. Ссылка, пересланная другому человеку, сама по себе входа не даёт.
5. После подтверждения только исходный браузер получает сессионный cookie и открывает панель. Если ссылка истекла, уже использована, вход отменён или бот не ответил, показать причину и предложить запросить `/admin` заново.

Сервер хранит только хеш случайного токена (не менее 256 бит энтропии), владельца Telegram ID, срок и статус запроса. Погашение токена и подтверждение выполнять атомарно. Ссылка не должна активировать вход простым GET: мессенджеры и антивирусы могут заранее открыть URL для превью. На странице входа не подключать сторонние скрипты, аналитику и внешние изображения; задать `Referrer-Policy: no-referrer`, `Cache-Control: no-store`. Не записывать токен в логи, историю действий или ошибки. Ограничивать частоту `/admin`, начала входа и подтверждений. Ссылку отправлять только в личный чат, без предпросмотра URL. Отказ постороннему пользователю — короткий нейтральный ответ без подробностей о списке администраторов.

Сессия: серверная, со случайным непрозрачным ID в cookie `Secure`, `HttpOnly`, `SameSite=Strict`; без `localStorage` и без JWT в URL. Время неактивности — 30 минут, абсолютный срок — 12 часов. Кнопка «Выйти» отзывает текущую сессию; административное исключение ID из `.env` и перезапуск сервиса отзывают все его сессии. На каждом запросе сервер проверяет действующую сессию и ID по текущему allowlist. Для операций изменения использовать CSRF-защиту и проверку `Origin`. [OWASP: сессии](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), [OWASP: одноразовые ссылки](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).

Для подтверждения нужны Telegram-обновления `callback_query`; их добавить в `allowed_updates` того же poller вместе с `message`, `channel_post` и `my_chat_member`. Обработчик личной команды `/admin` должен выполняться до маршрутизации сообщений чатов и не менять её результат. Если Telegram временно недоступен, новые входы невозможны; уже открытые сессии живут до своего срока.

## 4. Реестр «куда добавлены боты»

Реестр `discovered_resources` хранит для каждого Telegram/MAX объекта: платформу, тип (`chat`/`channel`), ID **строкой**, название, публичный username/ссылку при наличии, статус бота, права, время первого и последнего события, время последней проверки, связанный `pair_key` или «без пары». MAX ID может быть 64-битным и должен обрабатываться без потери точности. Отдельная таблица `discovery_events` хранит историю: `bot_added`, `bot_removed`, изменение прав, изменение названия, источник события и время. Повторные события не создают повторных записей о текущем объекте; журнал событий сохраняет хронологию без дублей одного и того же webhook/update.

Telegram наполняет реестр из `my_chat_member`, `message`, `channel_post`; MAX — из `bot_added`, `bot_removed`, `bot_admin_permissions_changed`, `chat_title_changed`, `message_created`. Для неизвестного объекта сохранять только метаданные, не пересылать и не журналировать текст поста. После обнаружения уточнять тип, название и права через доступные API. Если бот уже был добавлен **до** запуска нового реестра, историческое событие не появится автоматически: панель должна показывать дату начала наблюдения и инструкцию «создайте новое сообщение/пост или пере-добавьте бота»; для известного вручную ID предусмотреть безопасную проверку через API.

Панель показывает также событие потери прав или удаления бота и последствия для пары. Для остановленной из-за прав пары — причина и время. Пустой реестр не должен выглядеть как «бот нигде не добавлен», если сбор событий ещё не настроен.

## 5. Добавление и изменение пар через панель

Кнопки «Добавить пару чатов» и «Добавить пару каналов» открывают короткий мастер. Никакого редактирования YAML/JSON администратором:

1. Выбрать Telegram-источник из обнаруженных объектов нужного типа, по названию с показом ID и прав. Если объект не найден — открыть подсказку по добавлению бота и журналу событий. Расширенный ручной ввод ID допустим только после успешной проверки объекта через Telegram API.
2. Выбрать MAX-назначение из объектов того же типа. Для ручного ID требовать `GET /chats/{id}`, подтверждение типа, статуса бота и прав на публикацию.
3. Для **пары чатов** выбрать, включать ли MAX → TG, и явно указать режим отправителей для каждого направления: `all_non_bot` либо `allowlist`. Для **пары каналов** обратного направления и фильтра авторов нет.
4. Показать экран проверки: оба названия и ID, типы, направление, права ботов, не заняты ли объекты другой парой. Кнопка «Проверить доступ» ничего не публикует.
5. Сохранить новую пару **выключенной**. Отдельная кнопка «Включить» после повторной проверки активирует только новые события; старые сообщения не публикуются. При желании администратор отдельно нажимает «Отправить тест» и подтверждает, в какой MAX-чат/канал уйдёт тестовая публикация.

В списке пар доступны просмотр и смена названия, настроек разрешённых отправителей, обратного направления у чатов, временная остановка и возобновление. Смена любого ID требует повторного мастера и явного подтверждения обоих названий; предпочтительнее архивировать старую пару и создать новую. Архивирование сохраняет журнал и связь старых доставок, но прекращает дальнейшие публикации. Новые и изменённые пары применяются без перезапуска бота. Включение и изменение пары фиксируются в аудит-журнале с Telegram ID администратора, временем и значениями «до/после» без секретов.

Один Telegram-источник и одно MAX-назначение могут принадлежать только одной активной паре соответствующего типа. Чат нельзя выбрать в пару каналов и наоборот. У первой существующей пары все поля доступны только для просмотра; миграция переносит её прежние ID, allowlist и направление точно, без расширения доступа.

## 6. Доставки и действия с ошибками

Экран «Доставки» использует записи постоянной очереди из основного ТЗ. Фильтры: период, пара, направление, статус, тип медиа, исходный ID. Детали показывают попытки, техническую ошибку и целевой ID/ссылку при наличии; полный текст и медиа не сохранять для целей интерфейса. Для `failed` можно выполнить «Повторить» после исправления причины; для `unknown` автоматический или ручной повтор публикации запрещён, пока не проверено, не создался ли уже пост. Действия администратора записывать в аудит.

На обзоре и карточке пары показывать «последняя успешная доставка», «ошибки за 24 часа», «в очереди» и «потеряно право публикации». Обновление в реальном времени не обязательно: достаточно автообновления каждые 15–30 секунд и явной кнопки «Обновить».

## 7. Компоненты и хранение

Развернуть отдельный **веб-модуль** в текущем репозитории и Docker Compose, доступный по `https://admin.example.ru`. Он включает интерфейс и защищённый Admin API. Caddy завершает HTTPS и направляет запросы панели на внутренний порт; порт Admin API не публикуется напрямую в интернет. Бот и веб-модуль используют общий слой работы с БД и проверки маршрутов. Единственный Telegram poller остаётся в сервисе бота. Веб-модуль не вызывает Telegram `getUpdates` и не создаёт подписку MAX webhook.

Хранилище на одном VPS: существующая по основному ТЗ БД SQLite с WAL и постоянным volume либо другая согласованная БД. Административный API меняет пары в транзакции; бот читает актуальную версию настроек из БД и подхватывает изменения без рестарта. Не допускать чтения частично обновлённой пары. Если используются два процесса с одной SQLite, учесть `busy_timeout`, короткие транзакции, миграции только из одного процесса и резервное копирование. В БД добавить `admin_login_requests`, `admin_sessions`, `discovered_resources`, `discovery_events`, `pair_audit` поверх таблиц пар и доставок.

Нужны API-операции: начать/подтвердить/отменить вход; получить текущего администратора; получить обнаруженные объекты и события; проверить права объекта; список/создание/изменение/активация/пауза/архивирование пар; список доставок и разрешённые действия с ними; аудит; выход. Все операции, кроме начальной страницы и начала входа по токену, требуют сессию. В API выполнять ту же валидацию, что и в интерфейсе; скрытые кнопки не заменяют проверку прав на сервере. Только подготовленные параметры БД, ограничение размера запросов, экранирование отображаемых названий, rate limits и запрет CORS для посторонних origin.

`ADMIN_TELEGRAM_USER_IDS` и `ADMIN_WEB_URL` добавить в `.env.example` с вымышленными значениями и описанием. Действительные ID, токены и URL одноразового входа не коммитить. Логировать выдачу, подтверждение и отказ входа по Telegram ID и времени, **без самого токена и cookie**. Резервировать БД; журналы добавлений, доставок и аудита не удалять при обычном обновлении контейнеров.

## 8. Критерии приёмки панели

1. Разрешённый ID из `.env` получает ссылку по `/admin` только в личном чате. Посторонний ID и команда в группе не дают ссылку. Изменение username администратора не влияет на доступ.
2. Ссылка действует 5 минут и один раз. Повторная выдача гасит предыдущую. Открытие страницы сканером/простым GET не расходует ссылку. Пересланная ссылка без подтверждения из исходного Telegram-аккаунта не создаёт сессию.
3. Вход требует нажатия «Подтвердить вход» тем же администратором; чужой `callback_query`, повторное подтверждение и истёкший запрос отклоняются. Выход, истечение сессии и удаление ID из allowlist прекращают доступ ко всем Admin API.
4. После добавления ботов в Telegram-чат, Telegram-канал, MAX-чат и MAX-канал в панели появляются четыре записи с верными типами, названиями и ID. Их `bot_added`/`my_chat_member`, изменение прав и удаление видны отдельными событиями журнала.
5. Администратор создаёт через браузер пару чатов и пару каналов, выбирая найденные объекты. Ошибочная комбинация типов, занятый ID и нехватка прав блокируют включение с понятной причиной. После включения новые сообщения идут по новым маршрутам без рестарта.
6. Для чатовой пары обратное направление можно включить/выключить, для пары каналов оно отсутствует. Новая пара не переносит историю. Первая прежняя пара и её права остаются без изменений.
7. По контрольному посту в журнале доставок находятся исходный и целевой ID, тип вложения, статус, попытки и ошибка. `unknown` нельзя повторить вслепую; `failed` можно повторить после исправления причины.
8. Все изменения пар и тестовые публикации записаны в неизменяемый через интерфейс аудит-журнал с ID администратора. В логах HTTP, приложении и браузерном URL после входа нет одноразового токена или сессионного cookie.
