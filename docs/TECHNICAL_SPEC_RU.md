# Техническое задание: мост Telegram ↔ MAX для пар чатов и каналов

Дата: 28 сентября 2026 года. Версия ТЗ: 1.1. Статус: для оценки и реализации. Подробный проект панели: [ТЗ веб-администрирования](WEB_ADMIN_SPEC_RU.md).

Дополнение от 29 сентября 2026 года: по новому запросу владельца направление MAX → Telegram доступно также для пар каналов. Описанные ниже ограничения обратного направления каналов относятся к первоначальному объёму работ.

## 1. Цель и исходное состояние

Развить существующий бот в единый сервис с двумя типами независимых маршрутов:

1. **Пары чатов:** один чат Telegram ↔ один групповой чат MAX. Направление Telegram → MAX обязательно. Направление MAX → Telegram включается отдельно для каждой пары.
2. **Пары каналов:** один канал Telegram → один канал MAX. Обратного направления для каналов нет. В MAX публикация должна отображаться как пост канала, без подписи от имени бота.

Количество пар задаётся конфигурацией, без изменения кода. Расчётный масштаб: несколько пар чатов и не менее 20 пар каналов. Новые пары можно добавлять независимо друг от друга.

Текущий код реализует одну двустороннюю пару **групповых чатов**, передаёт текст и подписи к медиа, но не сами вложения. Для входа из Telegram используется long polling по `message`, для MAX — webhook. Имеются allowlist пользователей и запрет обработки посторонних чатов. Это следует считать **функционалом №1**: при миграции он становится первой парой чатов с сохранением прежних ID, разрешённых пользователей, оформления сообщений и включённого обратного направления. До изменения кода зафиксировать текущий коммит и версию развёрнутой конфигурации; секреты в Git не помещать.

## 2. Ожидаемое поведение

| Тип пары | Источник | Назначение | Направление | Обязательные форматы |
| --- | --- | --- | --- | --- |
| Чаты | Telegram group/supergroup | MAX chat | Всегда TG → MAX | Текст, фото, альбом фото, видео, аудио, подпись |
| Чаты | MAX chat | Telegram group/supergroup | Опция конкретной пары | Те же форматы, насколько они представлены API источника |
| Каналы | Telegram channel | MAX channel | Только TG → MAX | Текст, фото, альбом фото, видео, аудио, подпись |

Под «пересылкой» здесь понимается создание нового сообщения с тем же содержимым и типом медиа, а не встроенная функция *Forward*. В групповых чатах сохранять понятную атрибуцию автора по правилу пары; для первой пары использовать существующий формат. В каналах не добавлять имя Telegram-автора или служебный текст, если они не были частью исходного поста. Ссылки, переносы строк и подписи сохранять. Форматирование Telegram преобразовывать в поддерживаемый MAX HTML/Markdown с экранированием; неподдерживаемую разметку передавать читаемым текстом, без потери содержания.

Альбом Telegram определяется по `media_group_id`, собирается коротким настраиваемым окном ожидания и публикуется как **один** пост MAX с несколькими вложениями и одной подписью. MAX допускает до 12 изображений/видео в одном сообщении. Альбомы MAX → Telegram собирать в `sendMediaGroup` с учётом ограничений Telegram; если исходная комбинация платформой назначения не поддерживается, использовать несколько последовательных сообщений с сохранением порядка и явным статусом `partial`, а не молча терять элементы. [Telegram Bot API](https://core.telegram.org/bots/api), [медиа MAX](https://dev.max.ru/docs-api/use-cases/sending-messages/media).

Для одиночного фото результат должен отображаться фотографией, для видео — воспроизводимым видео, для аудиозаписи — аудиовложением с доступным воспроизведением, а не ссылкой или текстовой заглушкой. Голосовые сообщения учитывать отдельным подтипом: сохранять голосовой формат, если оба API позволяют; иначе передавать воспроизводимым аудиофайлом и фиксировать преобразование в журнале. Файлы других типов, стикеры, опросы, реакции, редактирование и удаление сообщений не входят в обязательный первый выпуск; их получать и отмечать как `unsupported`, не объявляя успешную доставку. Ответы на сообщения/треды и старую историю также не переносить в первом выпуске.

## 3. Конфигурация пар

Реестр маршрутов хранить отдельно от секретов, в БД и редактировать через защищённую веб-панель. Новая пара применяется без изменения кода, `.env` и перезапуска бота. Изменения проверять до применения, сохранять атомарно и резервировать. Пример логической структуры записей (это иллюстрация, не файл для ручного редактирования):

```yaml
chatPairs:
  - key: main-chat
    enabled: true
    telegramChatId: "-1001111111111"
    maxChatId: "-2222222222"
    maxToTelegram: true
    telegramSenders: { mode: allowlist, ids: ["123456789"] }
    maxSenders: { mode: allowlist, ids: ["987654321"] }
  - key: second-chat
    enabled: true
    telegramChatId: "-1003333333333"
    maxChatId: "-4444444444"
    maxToTelegram: false
    telegramSenders: { mode: all_non_bot }
    maxSenders: { mode: all_non_bot }

channelPairs:
  - key: news
    enabled: true
    telegramChannelId: "-1005555555555"
    maxChannelId: "-6666666666"
```

`key` — неизменяемый человекочитаемый идентификатор пары. ID хранить строками, поскольку MAX использует 64-битные значения: при приёме JSON нельзя терять точность целого числа в JavaScript. Для каждой пары проверить: тип источника и назначения, наличие ботов и нужных прав, уникальность `key`, отсутствие повторного использования Telegram-источника или MAX-назначения в парах одного типа. Пара не должна активироваться при неполной настройке. При смене ID панель повторно показывает названия объектов и требует явного подтверждения, чтобы опечатка не отправила контент в чужой чат/канал.

Политика отправителей задаётся отдельно для каждого направления чатовой пары: `all_non_bot` либо `allowlist`. Для новой пары режим выбирается явно при создании. Для старой пары существующие `TELEGRAM_ALLOWED_USER_IDS` и `MAX_ALLOWED_USER_IDS` импортируются без расширения доступа. Для каналов автор сообщения не фильтруется: авторизация осуществляется по точному ID канала и статусу бота в нём. Не пересылать сообщения самого бота и созданные этим мостом сообщения, исключить циклы при включённом обратном направлении.

Токены Telegram/MAX, секрет webhook, адрес панели и `ADMIN_TELEGRAM_USER_IDS` оставить в `.env`/секретах сервера. Записи пар в БД не должны содержать токенов. Новые пары настраиваются в панели; `.env` меняется только при изменении инфраструктуры или списка администраторов.

## 4. Обнаружение ID и добавление пары

Сделать **реестр обнаруженных объектов** (таблица `discovered_resources` и отдельный экран панели «Куда добавлены боты»), не зависящий от того, включена ли пересылка. Поля: платформа, тип (`chat`/`channel`), ID, название, публичная ссылка или username при наличии, статус бота, права, `first_seen_at`, `last_seen_at`, источник обнаружения и `configured_pair_key` при наличии. Отдельно хранить хронологию добавления/удаления и изменения прав. Текст сообщений и постов в этот реестр не писать.

Telegram: слушать `my_chat_member`, `message` и `channel_post`. При добавлении бота сохранять ID и тип чата/канала, при смене статуса обновлять реестр. Первое сообщение/пост — резервный способ обнаружения, если событие добавления было пропущено. Для неизвестных объектов сохранять только технические метаданные, **не пересылать и не логировать содержимое**. Учитывать, что бот не сможет получить задним числом список всех Telegram-чатов и старые посты: после настройки необходим новый тестовый пост/сообщение. [Telegram Bot API: Update](https://core.telegram.org/bots/api#getting-updates).

MAX: подписаться как минимум на `bot_added`, `bot_removed`, `bot_admin_permissions_changed`, `chat_title_changed`, `message_created`. На `bot_added` сохранять `chat_id` и `is_channel`, затем по `GET /chats/{chatId}` уточнять тип и название. При удалении или потере прав помечать объект недоступным и приостанавливать связанную пару. MAX не предоставляет готовый список всех чатов/каналов бота через `GET /chats`, поэтому реестр событий обязателен; пропущенный `bot_added` восстанавливать повторным добавлением бота либо другим документированным событием с ID. [MAX: получение chat_id](https://dev.max.ru/docs-api/use-cases/getting-chat-id), [MAX: события](https://dev.max.ru/docs-api/objects/Update), [MAX: сведения о чате](https://dev.max.ru/docs-api/methods/GET/chats/-chatId-).

Отдельный веб-интерфейс должен показывать найденные объекты и журнал событий, позволять создать пару через мастер выбора Telegram-источника и MAX-назначения, проверить названия/типы/права, сохранить новую пару выключенной и затем включить её. Вход — по `/admin` в личном чате Telegram-бота: временная одноразовая ссылка выдаётся только Telegram user ID из `ADMIN_TELEGRAM_USER_IDS` в `.env`; для защиты от пересланной ссылки вход подтверждается кнопкой в том же боте. Полный сценарий, экраны, сессии и API описаны в [ТЗ веб-панели](WEB_ADMIN_SPEC_RU.md). Пошаговая инструкция для владельца:

1. Добавить Telegram-бота в исходный чат/канал. Для группового чата разрешить получение всех сообщений (настроить privacy mode или соответствующие права), для канала — права, позволяющие получать новые посты. Для направления MAX → TG дать право отправлять сообщения и медиа в Telegram-чат.
2. Добавить MAX-бота в целевой чат/канал и дать права читать сообщения там, где включено направление MAX → TG, и публиковать везде, куда идёт доставка. Для MAX-канала бот должен иметь административное право `write`.
3. Отправить Telegram-боту `/admin` в личном чате, войти по временной ссылке и подтвердить вход в боте. Открыть экран «Куда добавлены боты». Если событие не появилось, создать тестовое сообщение/пост или повторно добавить бота.
4. Создать пару в панели, проверить типы и права, включить её и отдельно отправить тестовые текст и медиа. Для MAX-канала визуально проверить, что пост отображается **от имени канала**.

Создание пары не должно автоматически публиковать старые сообщения. Требуется явная отдельная операция для тестовой публикации, чтобы не отправить случайный пост при проверке.

## 5. Доставка и хранение состояния

Пайплайн: получить обновление → определить тип и пару → проверить источник/отправителя → сгруппировать альбом → сохранить задание → скачать медиа → загрузить медиа в MAX или Telegram → отправить сообщение/пост → сохранить ID результата и статус. Исходное обновление подтверждать только после устойчивого сохранения задания. Для MAX webhook нынешний ответ HTTP 200 отправляется до окончания обработки: в новой версии нужно гарантировать запись задания до 200, а затем обрабатывать его асинхронно.

Использовать постоянную очередь и БД (для одного VPS подходит SQLite с WAL и резервным копированием, в отдельном постоянном volume). Хранить пары, обнаруженные объекты, входящие события, задания, попытки и соответствие исходных/целевых ID. Уникальный ключ доставки: платформа + ID объекта + ID сообщения или `media_group_id` + направление + ключ пары. Повторные webhook/update не должны порождать повторную публикацию. Для MAX → TG сохранять также ID каждого сообщения, если альбом отправлен несколькими элементами.

Обрабатывать задания в порядке получения **внутри каждой пары и направления**; разные пары могут работать параллельно. Ограничить скорость MAX до документированного лимита 2 сообщения/с на один чат/канал и учитывать общий лимит запросов API. В Telegram учитывать `retry_after`/429. Ошибки сети, 429, временная недоступность API и `attachment.not.ready` должны вести к повтору с задержкой и ограничением числа попыток; отсутствие прав, неправильный ID и неподдерживаемый формат — к приостановке или явному `failed` с уведомлением. [MAX: отправка сообщений](https://dev.max.ru/docs-api/methods/POST/messages), [MAX: загрузка медиа](https://dev.max.ru/docs-api/methods/POST/uploads).

После неопределённого результата POST (разрыв связи после отправки) **не делать слепой повтор**, который может создать дубль. Помечать `unknown`, сверять результат по доступным API/истории и отдавать на ручную проверку, если определить исход нельзя. Абсолютную гарантию «ровно один раз» без поддержки идемпотентности принимающего API не обещать. При обычных повторах гарантировать отсутствие дублей по сохранённому ключу и результату.

## 6. Медиа и ограничения платформ

Для каждого вложения хранить тип, исходный ID/токен, MIME, размер, порядковый номер и привязку к подписи. Файлы передавать потоково или через временный каталог с лимитом места, проверкой MIME/расширения и гарантированной очисткой. Логировать технические ошибки, но не содержимое файла и не секретные URL загрузки. Каждому MAX-вложению получать отдельный токен загрузки. Аудио и видео в MAX передавать как соответствующие типы вложений; альбом фото/видео — одним постом с массивом вложений там, где API разрешает. [MAX: медиа](https://dev.max.ru/docs-api/use-cases/sending-messages/media).

Для видео в `channel_post` Telegram Bot API передаёт `file_id`, размер и другие метаданные, **не прямой URL исходного файла**. По `file_id` вызывается `getFile`, который возвращает `file_path`; только после этого можно построить URL вида `https://api.telegram.org/file/bot<TOKEN>/<file_path>`. Для обычного облачного Bot API Telegram документирует скачивание файлов до 20 МБ. Права администратора канала дают доступ к постам, но не отменяют лимит `getFile`. Стандартный Telegram-узел n8n использует ту же цепочку. Публичная ссылка на пост также не является прямой ссылкой на файл. [Telegram Bot API: Video, File и getFile](https://core.telegram.org/bots/api), [код Telegram-узла n8n](https://github.com/n8n-io/n8n/blob/master/packages/nodes-base/nodes/Telegram/Telegram.node.ts).

Для обязательной пересылки видео больше 20 МБ использовать локальный Telegram Bot API Server в составе этого проекта. Допустимая альтернатива для оценки исполнителем — работа с Telegram MTProto и скачивание файла частями через `upload.getFile`; этот метод доступен ботам, но не выдаёт простой постоянной HTTP-ссылки и усложняет реализацию. До выбора окончательного варианта показать прототип на исходных видео 10, 25 и 100 МБ, включая приватный канал: сравнить размер скачанного файла с `file_size` и проверить воспроизведение публикации в MAX. `api_id`/`api_hash` требуются для локального Bot API Server либо MTProto-клиента. [Локальный Telegram Bot API Server](https://core.telegram.org/bots/api#using-a-local-bot-api-server), [MTProto upload.getFile](https://core.telegram.org/method/upload.getFile).

Пределы MAX сохраняются независимо от способа скачивания: например, изображение до 50 МБ, видео до 250 МБ, аудио до 256 МБ/60 минут. Неподходящий формат или превышение лимита должны давать `failed` с понятной причиной и уведомлением, без подмены медиа ссылкой. Для обратного направления учесть ограничения загрузки Telegram и при необходимости использовать локальный Bot API Server. [MAX: типы вложений](https://dev.max.ru/docs-api/use-cases/sending-messages/attachment-types).

На прототипе проверить реальные события и скачивание MAX-медиа, особенно аудио и альбомов, до реализации полной очереди: документация описывает форматы входящих вложений, но результат «тот же вид в Telegram» должен быть подтверждён интеграционным тестом на используемом типе контента. Если конкретный тип API не отдаёт в скачиваемом виде, исполнитель документирует ограничение и предлагает согласуемый способ обработки; успехом считать нельзя.

## 7. Мониторинг и безопасность

Для каждого задания показывать в панели: время, пару, направление, тип контента, исходный ID, целевой ID при успехе, статус `queued`/`uploading`/`sent`/`retrying`/`unknown`/`failed`/`unsupported`/`partial`, число попыток и короткую ошибку. Нужны фильтры последних доставок и ошибок, а также агрегаты по каждой паре: последняя успешная отправка, размер очереди, возраст старейшего задания, число ошибок за сутки. Уведомление владельцу при потере прав, длительной ошибке, накоплении очереди или нехватке диска. Адрес/способ уведомлений вынести в секретную конфигурацию; не отправлять сообщения пользователям чатов при технической ошибке.

Доступ к веб-панели только через HTTPS и сессию администратора, полученную по `/admin` и подтверждённую в Telegram. Доступ к БД, серверным логам и временным файлам только у администратора сервера. HTTPS webhook MAX проверять по секрету, ограничивать размер тела и число запросов, отклонять события от неизвестных ID. Не считать само событие добавления бота разрешением на репост: публикация возможна только для явно включённой пары. Сверять фактический тип `chat`/`channel`; не разрешать маршрутизацию в личные диалоги. Секреты, ссылки входа и сессионные cookie не писать в логи, ротация журналов обязательна. Для скачивания медиа не следовать произвольным URL из сообщений: использовать адреса Telegram/MAX API и контролируемые URL загрузки, с защитой от обращений к внутренней сети. Для MAX int64 ID применять точный парсинг и строковое сравнение.

Резервировать БД и конфигурацию; документировать восстановление после сбоя VPS. Обновления приложения проводить с миграцией схемы и возможностью отката. Сохранить действующий HTTPS webhook, сертификатную цепочку MAX и контейнерный запуск. Не запускать одновременно два Telegram poller с одним токеном.

## 8. Этапы реализации

1. **Фиксация и регрессия.** Снимок текущего состояния, тестовые сценарии первой пары, подготовка миграции существующей `.env` в реестр без изменения поведения.
2. **Реестр и веб-администрирование.** БД, обнаружение Telegram/MAX объектов, `/admin` и вход по одноразовой ссылке с подтверждением, экраны реестра и журналов, мастер добавления/проверки/отключения пар, валидация ID и прав.
3. **Много чатов.** Несколько пар, обязательное TG → MAX и переключаемое MAX → TG, текст, защита от петель, сохранение старой пары.
4. **Медиа в чатах.** Проверить прототип скачивания видео больше 20 МБ. Затем реализовать одиночное фото, альбом, видео и аудио в обе стороны через локальный Telegram Bot API Server либо проверенный MTProto-вариант.
5. **Каналы.** TG `channel_post` → MAX-пост от имени канала, все обязательные медиа, 1 → 1 маршрутизация.
6. **Надёжность и эксплуатация.** Постоянная очередь, повторы, статусы, уведомления, резервирование, инструкция владельца и нагрузочная проверка на 20 канальных пар.

Этапы могут выпускаться по отдельности, но завершённым ТЗ считается только после выполнения всех обязательных требований и критериев ниже.

## 9. Приёмка

Исполнитель предоставляет исходный код, миграцию конфигурации, пример `.env` без секретов, веб-панель, инструкции установки/обновления/отката, описание ограничений и протокол проверок. Проверять на тестовых чатах/каналах Telegram и MAX, затем на одной реальной паре каждого типа.

1. После обновления исходная пара чатов работает как прежде: те же ID, allowlist, подписи и оба направления. Новые пары не меняют её настройки.
2. Добавлены минимум две новые чатовые пары: в одной выключено MAX → TG, во второй включено. Каждое сообщение попадает только в соответствующую пару; чужие чаты и личные сообщения игнорируются.
3. Добавлены минимум две пары каналов. Посты идут только TG → MAX, один исходный канал публикуется только в своём MAX-канале. На стороне MAX пост визуально опубликован от имени канала.
4. Во всех активных направлениях проверить: текст, одно фото без/с подписью, альбом из нескольких фото, видео без/с подписью, аудиозапись без/с подписью, голосовое сообщение. Контент остаётся медиа соответствующего типа, порядок альбома сохраняется, потерянных вложений нет. Для оговорённого преобразования голоса проверить воспроизведение и запись статуса.
5. ID новых объектов находятся в панели «Куда добавлены боты»; ясно видны тип, имя, права и статус. Журнал показывает события добавления, удаления и смены прав. Проверка в мастере выявляет удалённого бота, недостаточные права и перепутанные типы чат/канал до активации пары.
6. Повтор входящего обновления, перезапуск приложения и временная ошибка MAX не создают дубли при известном результате доставки. Неподтверждённый результат имеет статус `unknown` и требует сверки. После восстановления сети очередь продолжает обработку.
7. При медиа за пределами возможностей API либо недоступном исходном файле доставка получает понятную ошибку и уведомление; текст вместо медиа самовольно не публикуется.
8. 20 канальных пар одновременно сконфигурированы и обработали контрольные посты без пересечения маршрутов. Очередь соблюдает лимиты API, а журнал позволяет найти судьбу каждого поста.
9. До выбора архитектуры скачивания представлен протокол проверки исходных видео 10/25/100 МБ и приватного канала: способ получения файла, сравнение размера с `file_size`, сохранение качества и воспроизведение в MAX. Если выбран MTProto вместо локального Bot API Server, приведены причины и интеграционные тесты этого решения.
10. Критерии входа, добавления пар, журналов и аудита из [ТЗ веб-панели](WEB_ADMIN_SPEC_RU.md#8-критерии-приёмки-панели) выполнены; без входа по разрешённому Telegram ID Admin API не раскрывает данные и не меняет пары.

## 10. Решения, которые надо закрепить до начала кодирования

В этом ТЗ приняты следующие значения по умолчанию: первую пару мигрировать без изменения прав и закрыть её от редактирования через панель; новые пары включать только после явной проверки; историю, правки и удаления сообщений не синхронизировать в первом выпуске; веб-панель использовать только для администраторов из `.env`. Владелец проекта и исполнитель должны отдельно согласовать максимальный размер поддерживаемого исходного файла с учётом диска VPS и целевых платформ, срок хранения истории доставок и канал технических уведомлений. Эти решения не должны ослаблять требования о пересылке фото, альбомов, видео и аудио в поддерживаемых пределах API.
