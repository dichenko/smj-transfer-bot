# Переезд на новый VPS

Эта инструкция относится к текущему промежуточному выпуску. **Видео, фото и аудио как вложения пока не пересылаются.** Тексты поддерживаются; подписи к медиа первой пары уходят отдельно со статусом `partial`. Для проверки пересылки видео нужен следующий этап разработки.

## До переключения

1. Зафиксируйте коммит и защищённую копию `.env` старого сервера. Скопируйте `.env` на новый VPS вне Git. Проверьте в нём `TELEGRAM_SOURCE_CHAT_ID`, `MAX_TARGET_CHAT_ID`, оба allowlist и `MAX_WEBHOOK_SECRET`: при первом запуске новая версия **один раз** импортирует их в заблокированную от редактирования пару `main-chat`.
2. Добавьте в `.env` нового VPS `DATABASE_PATH=/app/data/bridge.sqlite`, `ADMIN_PORT=3700`, HTTPS-адрес `ADMIN_WEB_URL` и список `ADMIN_TELEGRAM_USER_IDS`. Не публикуйте токены и одноразовые ссылки входа.
3. Подготовьте Docker, каталог `data/` и `logs/` с владельцем UID 1000, свободное место под базу и будущие медиа. Проверьте `docker compose config --quiet`, затем `docker compose build`. **Не запускайте `bridge` параллельно со старым сервером:** один Telegram-токен должен иметь один poller, а отдельные БД не защитят от дублей при двух активных обработчиках.
4. Установите Caddy и адаптируйте `deploy/Caddyfile.example` для домена webhook и домена панели. Откройте наружу TCP 80/443; внутренние порты 3600/3700 оставьте на `127.0.0.1`. Проверьте A и AAAA для **обоих** имён, если используется IPv6. HTTPS-сертификаты и каталог данных Caddy должны переживать перезапуск.
5. Если DNS-провайдер позволяет, заранее уменьшите TTL записей и дождитесь истечения прежнего TTL. Понижение TTL непосредственно перед изменением IP не ускорит уже закешированные записи.

## Переключение

1. Выберите спокойное время и остановите старый `bridge`. Сохраните старый VPS и `.env` для отката. Не запускайте одновременно старый и новый процессы бота.
2. Измените A-записи webhook-домена и домена панели на IP нового VPS. Исправьте или удалите устаревшие AAAA-записи. Дождитесь, когда новый адрес виден через DNS; проверьте Caddy и действительный сертификат HTTPS для обоих имён.
3. Запустите `docker compose up -d --build` на новом VPS. Проверьте `docker compose ps`, `docker compose logs --tail=100 bridge admin` и локально `curl http://127.0.0.1:3600/health`. Первый запуск создаст SQLite и перенесёт старую пару из `.env`.
4. Проверьте активные MAX-подписки: `docker compose exec bridge npm run subscriptions`. Новый `bridge` вызывает `POST /subscriptions` при старте. При прежнем `MAX_WEBHOOK_URL` ручная смена URL не требуется; убедитесь, что подписка указывает на него и нет лишнего старого адреса. Если URL меняется, укажите новый в `.env`, запустите сервис, затем после проверки удалите **точную старую подписку** через `DELETE /subscriptions?url=<старый URL>`.
5. Напишите боту `/admin` в личном чате, войдите в панель и проверьте импорт `main-chat`. Отправьте новый контрольный текст в обе стороны; проверьте ID назначения и статус в журнале доставок. Для ранее добавленных тестовых чатов создайте новые сообщения: старые события добавления бот не получит задним числом.
6. Сделайте `docker compose exec bridge npm run backup` и сохраните полученный файл из `data/backups/` вне нового VPS.

## Что происходит при задержке DNS

Пока часть клиентов видит старый IP, запросы MAX могут ещё попадать на старый сервер. Если старый обработчик остановлен, MAX повторяет неуспешные webhook-запросы, но не бесконечно. Поэтому переключение и проверку HTTPS не следует растягивать. Telegram хранит неподтверждённые обновления не дольше 24 часов. Новая и старая версии с разными БД не имеют общей дедупликации, поэтому одновременная работа может дать дубли.

## Откат

Остановите новый `bridge` **до** повторного запуска старого. Верните DNS на старый IP и, если менялся URL подписки MAX, верните подписку на старый URL и прежний секрет. Сохраните новую базу для разбора заданий со статусами `queued` и `unknown`: старая версия не прочитает её очередь. После отката убедитесь, что текстовые тестовые сообщения доходят только один раз.
