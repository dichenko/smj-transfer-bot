# Telegram ↔ MAX bridge

Сервис получает обновления Telegram через один long poller и MAX через HTTPS webhook. Маршруты чатов и каналов хранятся в SQLite; панель администратора работает отдельным процессом и видит изменения без перезапуска бота. [Основное ТЗ](docs/TECHNICAL_SPEC_RU.md) и [ТЗ панели](docs/WEB_ADMIN_SPEC_RU.md) задают полную цель проекта.

Переезд со старого VPS описан в [пошаговой инструкции](docs/SERVER_MIGRATION_RU.md).

## Текущее состояние

- При первом запуске прежняя пара из `TELEGRAM_SOURCE_CHAT_ID`, `MAX_TARGET_CHAT_ID` и двух allowlist переносится в БД как `main-chat` («Функционал №1»). Она остаётся двусторонней и закрыта от редактирования через панель. Исходные значения `.env` после импорта не меняют запись в БД.
- В панели доступны вход через `/admin`, реестр обнаруженных объектов, журнал событий, создание выключенных пар, проверка прав, включение, пауза, архивирование, доставкa и аудит. Новые пары начинают работать сразу после включения.
- Текстовые сообщения идут по чатовым маршрутам в обе стороны и из Telegram-каналов в MAX-каналы. Для групп сохраняется подпись автора прежнего формата. В каналах подпись автора не добавляется.
- Одиночные видео из Telegram до 250 МБ передаются в MAX через локальный Telegram Bot API Server и загрузку медиа MAX. Для первой прежней пары подпись к медиа по старому поведению отправляется текстом (`partial`). Фото, альбомы, аудио, голосовые и прочие вложения пока получают `unsupported` для новых пар.
- Входящие задания сохраняются до подтверждения webhook; повтор одного источника не создаёт вторую доставку. Если результат POST неопределён, задание получает `unknown` и автоматически не повторяется. Полная гарантия доставки и интеграционные проверки платформ пока не завершены.
- Логи новых обновлений содержат технические метаданные и ошибки, без текстов посторонних сообщений и без полных JSON-обновлений. Команда `/logs` в личном чате доступна прежним разрешённым пользователям.

## Подготовка и запуск

Требуется Node.js 22 и Docker Compose. Скопируйте `.env.example` в `.env` на сервере и заполните секреты, включая `TELEGRAM_API_ID` и `TELEGRAM_API_HASH` из my.telegram.org/apps. Не помещайте `.env` в Git. `ADMIN_WEB_URL` должен быть публичным HTTPS-адресом панели, `ADMIN_TELEGRAM_USER_IDS` — список числовых Telegram user ID. Пустой список закрывает вход.

```bash
mkdir -p data logs
chown 1000:1000 data logs
docker compose up -d --build
docker compose logs -f bridge admin
```

Контейнеры используют один постоянный каталог `./data` для `bridge.sqlite` и SQLite WAL. `telegram-api` и `bridge` работают с UID 1000, чтобы мост мог читать скачанные видео из общего тома. `bridge` запускает миграции, `admin` ждёт его health check. Не запускайте второй Telegram poller с тем же токеном. Порт webhook и порт панели доступны только на loopback сервера; пример двух HTTPS-сайтов Caddy — в [`deploy/Caddyfile.example`](deploy/Caddyfile.example).

Перед первым переключением с облачного Telegram Bot API на локальный остановите `bridge`, запустите `telegram-api`, вызовите `logOut` на облачном API и затем запустите `bridge` с `TELEGRAM_API_ROOT=http://telegram-api:8081`. Так рекомендует [Telegram](https://github.com/tdlib/telegram-bot-api#moving-a-bot-to-a-local-server). Том `telegram_api_data` содержит скачанные файлы; он смонтирован в `bridge` только для чтения.

Перед первым обновлением рабочего VPS зафиксируйте коммит текущего деплоя и контрольную сумму серверного `.env` без вывода содержимого:

```bash
git rev-parse HEAD
sha256sum .env
```

Сохраните резервную копию `.env` в защищённом месте и остановите старый контейнер перед запуском новой версии. После создания базы делайте резервную копию через `docker compose exec bridge npm run backup`. Скрипт использует SQLite Backup API и проверяет целостность; файл появится в `data/backups/`. Копируйте его вне VPS по своему графику. Простое копирование работающей базы без WAL может быть неполным. Для отката остановите оба контейнера, восстановите совместимые версию кода и копию базы, затем запустите контейнеры снова. Не удаляйте `data/` при пересоздании контейнеров.

## Добавление пары

1. Добавьте Telegram-бота в исходный групповой чат или канал, MAX-бота — в соответствующий чат или канал. Выдайте права чтения и публикации. Для Telegram-группы настройте получение всех сообщений.
2. Отправьте `/admin` боту **в личном чате** с ID из `ADMIN_TELEGRAM_USER_IDS`. Откройте ссылку, нажмите «Продолжить вход» и подтвердите вход кнопкой в том же боте.
3. На экране «Куда добавлены боты» проверьте имена, типы и точные ID. Если объект не обнаружен, создайте новое тестовое сообщение или повторно добавьте бота.
4. Создайте пару. Она сохранится выключенной. Нажмите «Проверить», сверьте названия и ID, затем отдельно «Включить». Для чатов явно выберите политики отправителей; `allowlist` с пустым списком никого не пропускает. Для канала направление всегда Telegram → MAX.
5. Проверьте контрольный текст в обоих чатах или канале и запись на экране «Доставки». Тестовую публикацию панель пока не предоставляет; отправьте обычный новый тестовый текст в источнике.

Для видео больше 20 МБ требуется работающий локальный Telegram Bot API Server. Видео MAX ограничено 250 МБ; другие медиа пока не передаются.

## Проверка разработки

```bash
npm install
npm test
docker compose config --quiet
```

SQLite использует встроенный `node:sqlite` Node.js 22; это экспериментальный модуль данной версии Node и при запуске может показывать предупреждение.
